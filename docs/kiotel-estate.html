2 · How they connect

The two centres of gravity

kiotel-admin is the identity authority. It owns users, orgs, products, roles and every permission string in the suite (backend/src/rbac/constants.ts, ~1000 lines), signs EdDSA JWTs published at /.well-known/jwks.json, and issues svc_ service tokens. kiotel-space delegates all auth to it; kiotel_lox trusts its HMAC-signed admin calls. This is the single most important thing the old 4-repo graph was missing.

kiotel_web remains the data hub. Its /api/v1/external partner API and its kiosk Postgres are consumed by kiotel-space (transaction reports), the portal (session reports, housekeeping tasks), the autofill extension (live guest rows), and the chatbot (read-only NL→SQL). Everything guest-related still flows through it.

3 · The repos

kiotel-admin — admin.kiotel.co · 281 code files

What it is: Central identity provider + admin console ("Kiotel Auth") for the whole suite. Owns users, organizations, products, roles/permissions, sessions; issues EdDSA (Ed25519) JWTs for three registered products.
Stack: Fastify + TypeScript (ESM), Prisma on PostgreSQL 18 behind pgbouncer, Redis + BullMQ workers, Next.js App Router dashboard (BFF pattern).
Entry: backend/src/server.ts (:5001) · backend/src/worker.ts · frontend/app/layout.tsx (:3001)
Runs: Docker Compose with hardened containers (cap_drop ALL, read_only, no-new-privileges).
Auth model: BFF sessions (browser holds only an opaque cookie); trusted-peer S2S gate = loopback OR x-internal-secret OR DB-managed IP allowlist; service tokens scoped svc_<productCode>.
Naming trap: its x-internal-secret header collides with kiotel_web's Python-sidecar X-Internal-Secret mechanism but carries a different secret for a different purpose. Also, DASHBOARD_CLIENT_SECRET is dual-purpose: the BFF's session secret and the universal trusted-peer bypass.

kiotel-space — space.kiotel.co · 351 code files (largest)

What it is: Internal staff workspace: encrypted team chat (groups, DMs, pins, stars, reminders), tasks with recurrence/checklists/watchers, property-scoped announcements, departments, web-push. Plus a read-only Kiosk Transaction module that proxies kiotel_web's partner API behind per-user, per-device permission checks.
Stack: Express 5 + Socket.IO (Redis adapter), Prisma on PostgreSQL 17 (37 models), Redis 8, BullMQ workers (transcode/push/reminder), tus resumable uploads to MinIO + ffmpeg, Next.js PWA frontend.
Entry: backend/src/server.ts · backend/src/app.ts · backend/prisma/schema.prisma (929 lines)
Connects to: kiotel-admin (all auth, session-freshness checks every 30s/60s, inbound revocation), kiotel_web partner API (Bearer KIOSK_API_TOKEN), the kiosk object store (HMAC-signed expiring media refs).
Good pattern: kiosk.media.ts wraps public CDN URLs in HMAC-SHA256 signed expiring references so raw guest-ID-scan URLs never reach the browser.
Two weaknesses: chat messages use AES-256-CBC with no auth tag (confidentiality only — ciphertext is malleable; AES-GCM would be correct), and KIOSK_API_TOKEN is a single static bearer granting read access to every device on its allowlist — per-user scoping exists only inside this backend.

kiotel_lox — lox.kiotel.co · 47 code files

What it is: Hotel key-card encoding. A Go API licenses Windows devices, keeps a per-device encrypted key-encoder registry, and relays make_key/delete_key/read_key commands over WebSocket to a .NET tray agent, which drives SPLUS (HTTP) or LockGuru (file-drop) encoders.
Stack: Go (chi, pgx/sqlc, rueidis, goose) on PostgreSQL 18 + pgbouncer + Redis 8; .NET WinForms Windows agent.
Entry: backend/cmd/server/main.go (:8080) · kiotel_lox_application/Program.cs
Best security posture in the estate: HMAC-signed admin requests and responses with Redis nonce replay protection, AES-GCM (HKDF-derived) encryption of vendor config, hardware-fingerprint device licensing with admin re-approval on change, and an admin API deliberately unreachable from the internet (nginx returns 444).
Note: fully separate stack — no Socket.IO, no kio_ tokens, no platform DB. Only shares the kiotel.co domain and the Spaces bucket.

chatbot — 99 code files

What it is: Multi-service AI support chatbot. A FastAPI portal runs a LangGraph pipeline (guardrails → L1/L2 semantic cache → LLM classify-and-route → tools), with three backing services: a RAG step-guide, a NL→SQL "customer module" (Vanna), and a doc-chat service.
Stack: Python 3.11 / FastAPI ×4, LangGraph + LangChain, DigitalOcean Gradient AI inference, Ollama (qwen2.5:1.5b) as a free local model with circuit-breaker fallback to the paid LLM, PostgreSQL 16 + pgvector.
Authorization is self-declared. user_role and device_id come from client-supplied request metadata (portals/kiotel_chatbot/main.py:219-227), so any holder of the single shared API_TOKEN can claim any role. The doc-chat service documents its own gate as "not real auth".
NL→SQL reaches sensitive tables. The trained schema (services/customer_module/schema/schema_context.json) includes app_secrets, device_oauth, ext_oauth_codes, external_api_clients. The guard (sql_guard.py) is regex-based, not a SQL parser — defense rests on the read-only role and statement timeout.

Kiotel_portal_front — portal.kiotel.co · 208 code files

What it is: Internal company portal — helpdesk tickets, task manager, HR (face-recognition attendance), plus customer-facing kiosk transaction views.
Stack: Next.js 14 (App Router) + React 18 + Tailwind/MUI + face-api.js, backed by a 5,400-line legacy Flask monolith (96 routes).
Runs: two pm2 processes, no Docker.
The worst secret-hygiene in the estate — all committed to git: hardcoded MySQL credentials for 64.227.6.9 (server/server.py:66-71, :83-86); a second DB connection string with password (server/models.py:6); a real-looking 96-hex-char JWT_SECRET shared with the Node backend (server.py:100); a Gmail SMTP app password (server.py:2782); and a trivial Flask SECRET_KEY ('abcdefghij...', server.py:49). Login compares passwords in plaintext (server.py:346). Rotate all of these.

hr_kiotel_backend — 78 code files

What it is: Express backend for the HR/employee portal + careers site: attendance and clock-in/out with face recognition, shift scheduling, leave, inventory, tasks, careers applications.
Stack: Node (CommonJS) + Express 4 + Socket.IO, MySQL via two pools (hr_management and the kiotel DB), DigitalOcean Spaces, Google Sheets, PM2.
Authentication is effectively broken: passwords are compared in plaintext (routes/auth_v2.js:75 — the file's own header admits it); legacy /admin/login and /employee/login authenticate by unique_id alone and return the entire DB row; and middleware/inventoryAuth.js grants identity and admin/manager roles purely from client-sent x-user-id / x-user-role headers. JWT falls back to "CHANGE_ME_dev_secret" if the env var is missing.

kiotel_pms_autofill — Chrome MV3 extension · 5 code files

What it is: Links a browser to a Kiotel device via OAuth2 PKCE against the platform, pulls the active kiosk session's guest rows, and autofills them into any PMS screen (field-mapping picker, MutationObserver UI, Alt+I/Alt+N hotkeys).
Auth: OAuth2 authorization-code + PKCE (S256) via chrome.identity.launchWebAuthFlow, bearer device token in chrome.storage.local, hourly re-verification, extension ID pinned by RSA key.
Very broad footprint by design: content script runs on <all_urls>, all frames — guest PII passes through every page the user visits. Distribution is self-hosted (enterprise force-install), not the Chrome Web Store.
README is stale: it claims "autofill logic is not implemented yet — this version handles the auth link only", but scripts/content.js is a fully implemented 1,673-line engine.

4 · Cross-cutting findings

Security — ranked by urgency

1. Committed production credentials — Kiotel_portal_front/server/server.py and models.py carry live DB passwords, a shared JWT secret, and an SMTP app password in git history. Rotate every one and purge/rewrite history. (The previously-known hardcoded Deepgram key in audio_services/stt-tts-using-api-only/app/config.py:6 is still outstanding too.)
2. Plaintext passwords + header-trust auth — hr_kiotel_backend and the portal's Flask backend compare passwords in plaintext; inventory routes trust client-sent role headers. Anyone who can reach the API can self-elevate.
3. Self-declared roles in the chatbot — one shared API token plus client-supplied user_role governs access to an NL→SQL tool whose schema includes app_secrets and OAuth tables.
4. Unauthenticated public speech services — two GPU services with open WebSockets and wildcard CORS.
5. Public guest-ID media — kiotel-space's code documents that the platform serves guest ID scans, camera captures and signed PDFs as public CDN objects; anyone with the raw URL can fetch them. kiotel-space mitigates locally with signed refs, but the underlying objects stay public.
Bright spots: kiotel_lox (HMAC + AES-GCM + nonce replay protection), kiotel-admin (hardened containers, rotating EdDSA keys, HIBP breach checks), kiotel-space's BFF pattern (tokens never reach the browser), and the autofill extension's OAuth2 PKCE.

Architectural observations

  • Auth is mid-migration. kiotel-admin is a proper IdP, but only kiotel-space and kiotel_lox use it. The portal/HR family still runs its own plaintext-password auth, and kiotel_web/kiotel-pms have their own schemes. Three generations coexist.
  • Four separate database families: platform Postgres (kiosk), PMS Postgres, admin/space Postgres 17/18, and the portal/HR MySQL pair — plus a Bluehost-hosted MySQL from an older product.
  • Everything shares one storage bucket (kiotel-space on DigitalOcean Spaces): platform media, lox DB backups, admin DB backups, HR attendance photos.
  • Two subdomains the graph never knew about: admin.kiotel.co and space.kiotel.co, alongside portal.kiotel.co, careers.kiotel.co and lox.kiotel.co.
  • Referenced but absent: a Node backend at api.kiotel.co (the portal's newer backend) and a standalone Python face-recognition service — neither is in any of the 14 repos. The estate is not yet fully enumerated.

Docs vs. code discrepancies found

  • kiotel_pms_autofill README says autofill is unimplemented; it is fully built.
  • audio_services/stt-tts-using-api-only README claims ElevenLabs Scribe; the code uses Deepgram nova-3 exclusively.
  • guest_translation declares a max_ws_connections=50 limit that is never enforced anywhere in the code.
  • stt-tts-inhouse error messages reference a /languages endpoint and response schemas that no longer exist.
