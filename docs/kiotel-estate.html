1 · The estate at a glance

Kiotel is not one system. It is two loosely-coupled halves plus a scattering of satellites — and the most important structural fact is that the two halves have separate identity systems: the internal suite federates auth to kiotel-admin, the kiosk platform runs its own. They meet only on the data plane — the internal suite reads the kiosk platform through its partner API — never on the identity plane.

2 · How they connect (and don't)

hub identity staff tools guest / property / device speech & AI
The single most important structural finding: kiotel_web does not use kiotel-admin as its identity provider. A repo-wide grep for admin.kiotel.co, jwks, and EdDSA found nothing — the hub runs its own five-principal auth (HS256 agent/admin JWTs, device_secret_hash, kio_ partner tokens, ext-OAuth). So the identity planes stay separate — the internal suite federates to kiotel-admin, the kiosk platform does not. But the data plane is not isolated: the internal suite reaches into the kiosk platform as a partner-API client — kiotel-space holds a kio_ token to read transaction reports, and (found in the gap sweep) kiotel-admin itself calls /api/v1/external/devices with a partner token (kiosk-devices.service.ts). Two identity worlds, one shared data plane.

3 · The four core systems

These four are the product. They were previously mapped from documentation only; the detail below comes from reading their code.

kiotel_web — the hub · kioteldashboard.kiotel.co · 441 code files

What it is: The control plane of the whole check-in product. Express + TypeScript + Knex (raw SQL, no ORM) on PostgreSQL 17 + Redis, with a Socket.IO command hub and a Next.js frontend serving two portals — the agent dashboard (/dashboard, 24 panels) and the admin console (/admin, 28 pages).
How agents drive kiosks: an agent takes an exclusive Redis-backed control lock on a device (ctl:device:{id}, SET NX, 24h TTL — one agent per kiosk, with a takeover-request state machine), then relays CMD**… strings into the device:{id} room. The kiosk streams telemetry back: documentScanned, scannerStatus, sessionEvent, kioskAlert, appVersion. ws/messages.ts persists the results — CASHEVENT→cash_events, RATINGCOMPLETE→guest_rating, MSG→guest_msg_input.
Five distinct principals (this is the part the docs undersold): agent JWT (with token_version revocation + device-assignment check), admin JWT, kiosk device_secret, kio_ partner tokens, and extension/internal secrets.
The partner API (middleware/externalApiAuth.ts): SHA-256 lookup of the bearer in external_api_clients → is_active check → Postgres inet[] CIDR match on allowed_ips → per-device allow-list from external_api_client_devices → scope check. Tokens are issued in the admin console; the raw kio_ value is shown once, only its SHA-256 and an 8-char prefix are stored.
The ext-OAuth server (routes/extOAuth.ts): a full OAuth2 + PKCE(S256) authorization-code flow for the Chrome extension — mints a hashed 60-second one-time code into ext_oauth_codes bound to agent+device+challenge, then issues a device token into device_oauth.
ID-scan pipeline (routes/scanner.ts, 1,370 lines): a Redis-semaphore-gated classify → OCR → field-extraction flow across two in-repo Python FastAPI sidecars — id-classifier (:8100, FastMRZ/PassportEye/AAMVA) and ocr-service (:8200, PaddleOCR).
Data: owns the shared kiosk Postgres — 61 tables across 61 Knex migrations.
ID scan images are uploaded public-read. services/storage.ts:218 and :244 set ACL: "public-read" on both uploadImage() and upload() — so guest ID scans and extracted-info JSON are world-readable to anyone with the URL. This is the upstream cause of the mitigation kiotel-space had to build (HMAC-signed expiring media refs).
The Python sidecars' auth is not actually enforced. id-classifier/main.py:50-56 and ocr-service/main.py:47-53 gate every endpoint on X-Internal-Secret, but the Node callers (services/id-classifier.ts, services/ocr-service.ts) never send the header. Either the sidecars are reachable without it, or this path is broken in production — worth an immediate check.
Possible SQL injection in routes/externalTransactionReports.ts: the ID-list clause is built by string interpolation rather than ? placeholders, in the most-exposed partner endpoint. Also: a plaintext device_secret fallback survives in three auth paths (deviceAuth.ts:30, authOrDevice.ts:49-51, ws/index.ts:139) despite a migration dropping the column; a duplicate POST /auth/refresh is registered twice; and an unresolved git merge conflict is committed in deploy/dev_nginx/kdashboard.porygonlabs.dev.conf:11-18.

kiotel_hardware — the lobby kiosk · .NET WinForms + WebView2 · 104 code files

What it is: The physical self-service terminal. A thin WinForms shell hosts WebView2 pages served by the platform; frmMainScreen is the god-form that holds the Socket.IO connection, the device REST client, and every peripheral driver (ID scanner, cash recycler, key encoder, IO board, camera, printer).
The RELAY contract, measured: processCommand implements exactly 86 command cases (lines 2414–3168) plus a prefix-matched SHOWANIMATION-<1..12> family. The wire format is a delimited string, not JSON: RELAY:<from>:CMD**<COMMAND>**<param>**<lang>.
Talks to: kiotel_web (Socket.IO + ~10 REST surfaces: config, secrets, licensing, scanner, camera, legal docs, media, guestban token) and audio_services (direct audio-ingest WebSocket with per-frame HMAC). Nothing else — grepped and confirmed.
The action-less avatar is real, not just documented. AiAvatarService.RunTurnAsync's only sink for LLM output is _tts.SpeakAsync(...) — there is no path from model output back into processCommand. A guest can make the avatar say something off-script; they cannot make it dispense cash or keys. This is the estate's best security design decision.
Elevation + a shipped credential: the app manifest requests requireAdministrator, and kiosk.csproj:49 ships a Google Cloud service-account JSON as a build artifact. Combined with an updater that launches an arbitrary installer, that is a meaningful supply-chain surface. Also, the avatar's entire persona is a hardcoded C# string describing a fictional Austin hotel with invented rates.
Docs corrected: DEVICES.md claims on-device SQLite — no file references SQLite at all. INTEGRATIONS.md attributes Google Meet to frmGoogleMeet.cs, which is never instantiated. The YOLO11 approach- detection service has zero callers. CASHEVENT is listed as a socket event; it is not.

audio_services — call recording + AI audit · FastAPI · 101 code files

What it is: The platform starts/stops recording via internal-secret HTTP; the kiosk streams call audio straight here over WebSocket (HMAC per frame); the service transcribes with Deepgram, runs an LLM compliance/quality audit shaped by per-hotel property rules pulled back from the platform, and posts the result to POST /api/v1/internal/ai-audit, which upserts session_ai_audit.
Shape: the deployed service is app/; the sibling folders (conversation-intelligence, k_trans_pipe, stt-tts-using-api-only) are WIP forks, not deployed paths.
Hardcoded live-looking Deepgram key at stt-tts-using-api-only/app/config.py:6 — still outstanding. And two of the three deployed services are entirely unauthenticated: audio_audit_transcript exposes /transcribe, /acoustic-features and /analyze with no auth at all.
Operational limits worth knowing: audits effectively never retry (audio_audit_max_attempts defaults to 1, and the sweeper filters on attempt_count < max), and the service cannot scale horizontally — the session registry, rate limiter and audit semaphore are all in-process behind an fcntl flock that hard-fails a second instance.
Fraud results never leave this repo. Docs say the fraud fields are posted back to the platform; the actual callback payload (app/audit.py:250-259) carries only session_id, agent_rating, remark_for_agent, report, status. Fraud/rating-manipulation detections stay in this database. Docs also have the ingest direction backwards — kiotel_web generates the per-session HMAC key, not this service.

kiotel-pms — pms.kiotel.co · standalone PMS · 274 code files

What it is: A complete property-management system — properties, room types, rate plans, tax/addon config, a tape-chart booking calendar, walk-ins, check-in/out, folio — with its own Postgres, its own argon2 + rotating-refresh auth, and three portals (admin / operator app / mobile staff).
Reservation lifecycle is a hard whitelist (RESERVATION_TRANSITIONS, property-enums.ts:180-190) enforced in changeReservationStatus — the structure a future CRS integration would plug into.
The headline correction: there is no partner-API client. A repo-wide grep for outbound HTTP found nothing calling kiotel_web. Its own docs/INTEGRATIONS.md and SYSTEM.md describe a live "Bookings exchange PMS ⇄ platform (partner API)" integration — it does not exist at HEAD. The nginx config actively forbids the browser from reaching other kiotel origins. The only thing it shares with the estate is the storage bucket (prefix-isolated under kiotel_pms/).
Confirmed double-booking race. The room-overlap check in createReservation (reservation.service.ts:144-151) runs on the pooled connection before the transaction opens — so two concurrent bookings can both pass. Present in two places. The repo's own docs list this as a "risk"; the code shows it is real.
Channel manager is schema-only. The CHANNEL_MANAGER_PROVIDERS enum (siteminder, cloudbeds, staah, …) exists as a dropdown and DB constraint with zero sync logic behind it. Good news for the SynXis plan: the slot is genuinely empty, not half-built.

4 · The identity & staff cluster

kiotel-admin — admin.kiotel.co · the IdP · 281 code files

What it is: Central identity provider and admin console for the internal suite. Owns users, organizations, products, roles/permissions and sessions; signs EdDSA (Ed25519) JWTs with DB-stored rotating keys published at /.well-known/jwks.json; issues svc_<product> service tokens. Every permission string in the suite lives in backend/src/rbac/constants.ts (~1,000 lines).
Stack: Fastify + Prisma on PostgreSQL 18 behind pgbouncer, Redis + BullMQ, Next.js BFF dashboard. Hardened containers (cap_drop ALL, read_only, no-new-privileges), HIBP breach checks, partitioned audit tables.
Two traps: DASHBOARD_CLIENT_SECRET is dual-purpose — the BFF's session secret and the universal trusted-peer bypass. And its x-internal-secret header collides by name with kiotel_web's Python-sidecar mechanism while carrying a different secret for a different purpose.

kiotel-space — space.kiotel.co · staff workspace · 351 code files (largest)

What it is: Encrypted team chat (groups, DMs, pins, stars, reminders), tasks with recurrence/checklists/watchers, property-scoped announcements, departments, web-push — plus a read-only Kiosk Transaction module that proxies kiotel_web's partner API behind per-user, per-device permission checks.
Stack: Express 5 + Socket.IO (Redis adapter), Prisma on PostgreSQL 17 (37 models), BullMQ workers, tus resumable uploads to MinIO + ffmpeg, Next.js PWA.
Auth: a genuine BFF — the browser holds only an opaque 32-byte session cookie; kiotel-admin's tokens live in Redis and never reach the client. Session freshness is re-checked against the IdP every 30s (HTTP) / 60s (sockets), with push revocation.
Good pattern: kiosk.media.ts wraps the platform's public CDN URLs in HMAC-signed expiring references, so raw guest-ID-scan URLs never reach the browser — a local fix for an upstream problem it doesn't own.
Two weaknesses: chat messages use AES-256-CBC with no auth tag (malleable ciphertext; AES-GCM would be correct), and KIOSK_API_TOKEN is a single static bearer covering every device on its allow-list — per-user scoping exists only inside this backend.

kiotel_lox — lox.kiotel.co · door-key encoding · 47 code files

What it is: A Go API licenses Windows devices, keeps a per-device encrypted key-encoder registry, and relays make_key/delete_key/ read_key over WebSocket to a .NET tray agent driving SPLUS (HTTP) or LockGuru (file-drop) encoders.
Best security posture in the estate: HMAC-signed admin requests and responses with Redis nonce replay protection, AES-GCM (HKDF-derived) encryption of vendor config, hardware-fingerprint licensing with admin re-approval on change, and an admin API deliberately unreachable from the internet (nginx returns 444). If a security baseline is ever written for Kiotel, start from this repo.

5 · Speech, AI & the long tail

chatbot — LangGraph support assistant · 99 code files

What it is: A FastAPI portal running a LangGraph pipeline (guardrails → L1/L2 semantic cache → LLM classify-and-route → tools), with a RAG step-guide service, an NL→SQL "customer module" (Vanna), and a doc-chat service. The platform proxies agent chat to it server-side via POST /api/v1/chat, attaching CHAT_API_KEY.
Models: DigitalOcean Gradient AI inference, with Ollama (qwen2.5:1.5b) as a free local receptionist model behind a circuit breaker.
Self-declared authorization. user_role and device_id come from client-supplied request metadata (portals/kiotel_chatbot/main.py:219-227) — any holder of the single shared API_TOKEN can claim any role. The doc-chat service documents its own gate as "not real auth".
NL→SQL reaches sensitive tables. The trained schema includes app_secrets, device_oauth, ext_oauth_codes, external_api_clients — i.e. the platform's own credential tables. The guard is a regex whitelist, not a SQL parser; safety rests entirely on the read-only role and statement timeout.

Kiotel_portal_front & hr_kiotel_backend — portal.kiotel.co · 208 + 78 code files

What they are: The internal company portal — helpdesk tickets, task manager, HR with face-recognition attendance, shift scheduling, leave, inventory, careers — plus customer-facing kiosk transaction views that consume the platform's partner API and push housekeeping tasks to kiosk devices. A Next.js 14 frontend, a 5,400-line legacy Flask monolith (96 routes), and a newer Express/MySQL backend, mid-migration.
Live production credentials committed to git (values not reproduced here): MySQL credentials for 64.227.6.9 (server/server.py:66-71, :83-86), a second DB connection string with password (models.py:6), a real-looking 96-hex-char JWT_SECRET shared with the Node backend (server.py:100), a Gmail app password (server.py:2782), and a trivial Flask SECRET_KEY (server.py:49).
Authentication is effectively broken: passwords compared in plaintext in both backends (server.py:346, routes/auth_v2.js:75 — the latter's own header comment admits it); legacy /admin/login and /employee/login authenticate by unique_id alone and return the entire DB row; and middleware/inventoryAuth.js grants admin/manager roles purely from client-sent x-user-id / x-user-role headers.

kiotel_pms_autofill — Chrome MV3 extension · 5 code files

What it is: Links a browser to a Kiotel device via OAuth2 PKCE against the platform, pulls the active session's guest rows (including 27 synthetic OCR fields the platform derives), and autofills them into any PMS screen — field-mapping picker, MutationObserver UI, Alt+I/Alt+N hotkeys. Self-hosted (enterprise force-install), not the Chrome Web Store; the platform serves its update manifest.
Broad by design: the content script runs on <all_urls>, all frames — guest PII flows through every page the operator visits. README claims autofill "is not implemented yet"; it is a 1,673-line engine.

7 · Security findings, ranked

1 · Committed production credentials — Kiotel_portal_front (MySQL passwords, shared JWT secret, SMTP app password) and the still-outstanding Deepgram key in audio_services. Rotate every one, then purge history.
2 · Guest ID scans are world-readable — the platform uploads scan images and extracted-info JSON with ACL: "public-read". This is guest PII (passports, driver's licences) on a public CDN. Highest-severity data-exposure item.
3 · Broken authentication in the portal/HR cluster — plaintext password comparison, passwordless legacy logins returning full DB rows, and role assignment from client-sent headers.
4 · The chatbot's NL→SQL can reach credential tables behind self-declared roles and a regex guard.
5 · Unenforced sidecar auth + possible SQLi in kiotel_web — the X-Internal-Secret header the Python sidecars require is never sent by their callers, and the busiest partner endpoint interpolates an ID list into raw SQL.
6 · Unauthenticated public services — two GPU speech services and two of three audio_services endpoints, all reachable with no credential.
Bright spots worth copying: kiotel_lox (HMAC + nonce + AES-GCM), the kiosk's structurally action-less avatar, kiotel-space's BFF token isolation, kiotel-admin's hardened containers and rotating EdDSA keys, and the extension's OAuth2 PKCE.

8 · Architectural observations

  • Auth is three generations deep. Modern federated identity (admin/space/lox), the platform's own five-principal scheme, and the portal's plaintext-password legacy — all running in production simultaneously.
  • Five database families: platform Postgres (kiosk, 61 tables), PMS Postgres, admin Postgres 18, space Postgres 17, and the portal/HR MySQL pair — plus a Bluehost-hosted MySQL inherited from an older product.
  • The storage bucket is the real shared substrate. Platform media, PMS documents, lox and admin DB backups, and HR attendance photos all live in the same DigitalOcean Space, separated only by key prefix.
  • Six subdomains: kioteldashboard, admin, space, portal, careers, lox, pms — plus videocall and hkbackend referenced from kiosk code.
  • Referenced but absent from all 14 repos: a Node backend at api.kiotel.co, a standalone Python face-recognition service, the guestban third-party scan service, and hkbackend.kiotel.co. The estate is not yet fully enumerated.
  • kiotel-pms is the odd one out — a complete, competent product with no runtime relationship to anything else Kiotel runs. Whether that is deliberate isolation or an unfinished integration is the single biggest open question in the estate.
